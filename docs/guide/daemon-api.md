# daemon API

The HTTP + JSON API that feld daemon provides. It consists of two surfaces, the [Control API](../spec/concepts/glossary.md#control-api) and the [Runtime API](../spec/concepts/glossary.md#runtime-api), and the CLI ([`cli.md`](cli.md)), Web UI, Runtime Adapters, and Collector all reach the daemon through this API. The request, response, and errors of each API are in the OpenAPI definition [`daemon-api.openapi.yaml`](daemon-api.openapi.yaml); the `feld-daemon` tests check it against the routes, and Web UI type generation checks it against the schema. This document describes the rules common to the API. Concepts and terms follow [`concepts/glossary.md`](../spec/concepts/glossary.md).

## Common conventions

- Authentication: the daemon listens on loopback, and requests from other devices come through an HTTPS proxy (`tailscale serve`) ([`auth.md`](../spec/design/auth.md#assumptions-and-trust-boundary)). The destination name is limited to loopback names and names allowed with `--allow-host` ([Accepted Host](../spec/design/auth.md#accepted-hosts)). Tokens are the four kinds in the glossary entry [token](../spec/concepts/glossary.md#token) (local token, browser token, Session token, internal token). A browser token is accepted only as the pair of a cookie and the key in the `X-Feld-Browser-Key` header; the others are accepted via `Authorization: Bearer`. The Control API can be called with a local token, browser token, or Session token, and the token used determines the value of `spawner` in spawned, `from` of a Message, and the requester of stop / kill. A Session token can call only operations on itself and operations opened by the grants of the Session's Actor, and gets 403 for anything else ([Authorization decisions](../spec/design/auth.md#authorization-decisions)). Pairing management accepts only the local token ([pairing](../spec/design/auth.md#pairing)). The Session token value appears only in the attach response and is masked in other responses ([`auth.md`](../spec/design/auth.md#preventing-token-exposure))
- Runtime API: the target is always the caller's [self](../spec/concepts/glossary.md#runtime-api). Runtime Adapter helpers and the CLI's `feld self` call it with a Session token, and the Collector with the internal token; telemetry is attributed to a Session by the [telemetry token](../spec/design/auth.md#session-token) the Runtime Adapter puts in a header. Distribution and resolution of Session tokens are described in [`auth.md`](../spec/design/auth.md#distributing-the-session-token), and the environment variables passed to the Runtime in [`plugin.md`](../spec/design/plugin.md#what-core-provides)
- Paths: requests reach the API listener over TCP; Runtime Adapter components also use the Feld home socket (`$FELD_HOME/daemon.sock`), and the CLI inside the Runtime's sandbox uses a file path ([spool](../spec/design/spool.md)). The spool accepts only Session tokens, and the request and response contents are the same as over TCP
- For requests authenticated with a browser token other than `GET`, the daemon returns 403 when `Origin` does not match the request's destination ([`auth.md`](../spec/design/auth.md#cookie-and-key))
- A Session token is valid only while its Session has no `end` and it is the last token issued to that Session. Runtime API requests with a closed Session's token (mailbox reads and writes, Runtime identity) and requests that determine `spawner` / `from` / the requester (`start`, `restart`, `send`, stop / kill) are rejected as session closed
- Errors: the response is `{message, next}` JSON. `next` is the next step a person takes, and only rejections that can show one (Workspace missing, executable needed to start missing) have it. Only the 403 for a request whose destination name is not allowed is human-readable plain text ([Accepted Host](../spec/design/auth.md#accepted-hosts)). The daemon checks the token before reading the request body and query, so a request whose token is not accepted gets an authentication error (401 / 403 / 409) regardless of its format. Boolean queries (`includeDeleted`, `current`, etc.) are true without a value
- Workspace: an Actor's `name` is unique within a Workspace, so resources referred to by name sit under `/v1/workspaces/{workspace}/actors/{actor}`. Resources with an ID (Actor `id`, Session, Message) are referred to directly, independent of Workspace, as in `/v1/sessions/{sessionId}`. A read with a `workspace` query covers all Workspaces (with a Session token, the Session's Workspace) when the query is omitted. The Actor references in records and Messages are the Actor `id`, and reads return them with the `name` and Workspace
- Name grammar: Workspace keys and Actor `name`s match `^[a-z0-9][a-z0-9-]*$`. Requests that give a name (`POST /v1/workspaces`, `POST …/actors`, `PATCH …/actors/{actor}`, `POST …/attach`) reject names that do not match the grammar with 400
- Soft delete: `delete` records `deletedAt`. Deleted items drop out of name-based paths and lists, and are reachable through lists with `includeDeleted` and references by ID
- Time range: `start` / `end` (RFC 3339, `[start, end)`). Reads that return time series accept `bucket` (bin width in seconds)
- Appended sequences (records, Session logs) are read further with the `after` cursor
- Derived values (outcome, attention, waiting, waiting count, unread-mail mark, skip mark, unlinked mark, next run, turn) are not records. Reads return them alongside the facts they derive from, and writes do not accept them

## Real-time updates

`GET /v1/events` notifies resource changes by kind and ID over SSE. It carries no values; the client redoes the relevant read. Clients that cannot use SSE call the same reads periodically instead. How the Web UI combines reads and notifications to draw is described in [`webui.md`](../spec/design/webui.md).
